# Issue 99: window-only Mac writer candidate

This checkout contains an implementation candidate, not a fully verified capture fix. The scope is a six-second Finder `--window` recording's movie cadence. The integrated runtime head `652afe7` built and passed the full suite on an isolated macOS VM; its installed app produced a decoded six-second CLI Window control. An earlier runtime (`0872c51`) also produced CLI and installed-app GUI captures near the requested endpoint. Native failure diagnostics now cover a real rejected timestamp and a forced outer timeout, but live microphone signal under slow finalization remains unproved. Do not ship it as a verified recording fix yet.

## Scope and privacy boundary

Only `CaptureMode::Window` creates `helper/RealtimeWriter.swift`'s app-local writer and SCK image callback. Display and Region keep the existing `SCRecordingOutput` setup, midpoint clock, content-filter exclusions, region source rectangle, screenshot sampler and teardown. They never create a candidate, convert a raw movie through the new writer, or enter its 26-second finish budget. Their filter selection retains main's display fallback. This preserves existing behavior; it is **not** a new privacy certification of Display/Region movies.

The helper has no continuous movie prompt-exclusion mechanism. `helper/ScreenProbe.swift` only takes a permission-probe screenshot with an empty exclusion list. Existing movie exclusions live in Rust: `SystemPrompts` polls CoreGraphics, lists prompt IDs in SCK, updates the stream content filter, drops potentially affected screenshot candidates and pauses screenshots for prompts SCK cannot exclude. These existing mechanisms remain. A forced post-stop check also drops screenshot candidates affected by a prompt still present after teardown. It does not certify a prompt that appeared and disappeared wholly during synchronous native stop, or a prompt missed between polls. Solving that pre-existing movie boundary requires a separately scoped native mechanism and Mac proof; #99 does not manufacture one or disable all Display/Region bundles instead.

The new Window path pins window ID, owner PID and bundle ID. Every filter lookup must resolve that owner and builds a window-only filter; loss of the window cannot become a display capture. Other applications' system-prompt windows are outside that source, including during synchronous stop. A fresh stop image must resolve the same owner and geometry. This is source isolation, not a promise that application-owned dialogs or arbitrary sensitive window contents are redacted.

`unsafe_video` rejects a failed new Window stream, not all legacy movies. With no movie, safe screenshot-only capture still builds a bundle. With no safe screenshots, finalization still refuses to decode an untrusted raw movie into a bundle and retains the existing recovery guard. A candidate error, bad screenshot, identity change or timeout preserves the independently stopped original window movie. Candidate failure is not itself evidence that the original contains different pixels.

## Candidate publication and lifetime

Rust passes borrowed SCK `CMSampleBuffer` pointers synchronously to a versioned Swift ABI. Swift retains each accepted sample before returning, releases it after serial-queue consumption, and bounds pending samples. One pixel-buffer adaptor writes stream samples and the final real screenshot on the same fixed canvas. Native PTS is mapped onto the existing capture/video-offset clock and implausible jumps fail the candidate.

The stop screenshot is timestamped at actual capture completion, strictly after the last accepted PTS and within 500 ms of the stop request. Finish and bounded native tail validation must succeed before atomic replacement. Validation checks the last decoded image against the screenshot and its packet endpoint. Only the waiting caller can publish; a timed-out worker can only delete its candidate. The CLI stops microphone input concurrently with screen finalization; GUI cancel now stops it before screen teardown. The maximum candidate wait remains 26 seconds for Window only. A diagnostic 30-second delay in the native finish entry point exercised the Rust outer timeout on `652afe7`; it does not prove AVFoundation's internal timeout. The original movie's hash was unchanged after the CLI returned and after an additional wait. The CLI process exited with a private candidate scratch file still present, which the ordinary retention sweep must remove; no late publication was observed.

The dylib loader uses one process-lifetime `OnceLock`, including cached load/symbol errors. It no longer takes a new `dlopen` reference per capture. It deliberately does not unload: Swift queue and AVFoundation completion closures can outlive destroy or finish timeout. A failed load requires process restart after repairing the installed dylib. Existing media leases and scratch retention are unchanged by this correction.

## Verification and remaining Mac proof

Linux checks cover the mode gate, pinned identity rejection, stop-frame timestamp constraints, validation-before-replacement, timeout/late-worker cleanup and safe screenshot-only finalization. Python source-wiring checks cover the legacy path, window-only candidate, singleton loader, packaging and publication checks. Linux test builds also compile the SDK-independent Rust ABI caller; this does not compile the SCK adapter or Swift library.

An earlier Mac VM passed the full suite (502 passed, 3 ignored) and captured two static six-second Finder windows, a moving/resizing Finder window and an Applications–Home–Applications sequence. On a later head (`d5eae998`), Mac tests passed (506 passed, 3 ignored); the production-ABI fixture, installed app signature, static and moving CLI Window, GUI Window, Display and GUI Region captures were exercised. That static movie was not retained for independent packet and stop-pixel inspection. On integrated runtime head `0872c51`, the Mac suite passed (522 passed, 3 ignored), the production-ABI fixture decoded the genuine six-second green stop frame, and the installed app passed signature verification and launched. New static and moving/resizing Finder CLI Window movies reached 5.898 and 5.953 seconds in their last coded packets; their decoded start/end frames and the retained static movie were inspected privately. A same-target GUI Window movie reached 30.792 seconds of a 30.877-second bundle with 105 ordered packets; GUI Region also captured and decoded the chosen rectangle. An ambiguous Finder request was refused. A default three-second Display CLI bundle decoded but contained only 0.85 seconds of legacy movie; the Display path was not changed here.

At `652afe7`, the Mac suite passed (525 passed, 3 ignored), the production ABI fixture passed, and the installed app's signature verified. A six-second Finder Window control decoded to a 6.023-second movie with Finder pixels at the end. A diagnostic dylib copied outside the checkout injected a duplicate PTS through the genuine native enqueue, yielding error 3 and a retained, decodable original movie; a separate forced 30-second finish delay triggered the Rust outer timeout and left the original file hash unchanged across a later check. The diagnostic library was removed and the production app reinstalled before the control recording. Production ABI negative fixtures rejected duplicate PTS, a missing final image and mismatched stop pixels. A real Finder owner-loss run retained a shorter decodable movie without exposing another application window; its contact sheet, however, contained a black frame after the window closed. These diagnostic runs do not establish every encoder/callback failure or a recycled window ID. The VM's disposable BlackHole input and an independent ffmpeg input capture both received silence while `afplay`/`ffplay` sent a synthetic tone to the selected output. Thus the virtual audio route never established nonzero input; saved audio under slow finalization is still unproved. All bundles and screenshots remain private.

The merged `main` candidate `6dcf937` built on a fresh macOS 26.6.2 VM (after installing the missing Xcode Metal toolchain), passed the full Mac suite (539 passed, 3 ignored), and passed the production Swift ABI fixture with three decoded frames and the green stop image at 6.0 seconds. The installed, ad-hoc-signed app passed `codesign --verify --deep --strict`; a six-second Finder “Recents” CLI Window recording decoded through 5.995 seconds with a 6.012-second movie duration and Finder pixels in its private contact sheet. The bundle's `audio.wav` existed but measured −91 dB peak. After installing BlackHole 2ch, restarting CoreAudio and selecting BlackHole as both default input and output, an independent ffmpeg input capture of an `afplay` 730 Hz tone also measured −91 dB peak. This again leaves nonzero microphone capture and GUI Cancel with real input unproved. The disposable VM was stopped and its cleanup confirmed; the owned test cost was $0.20. No private bundle or image was published.

Before marking this ready: prove working microphone audio under slow finalization and GUI cancel, and cover unexercised callback/encoder failure, recycled ID, rejected/slow screenshot and native finish timeout as appropriate. The owner-loss black keyframe deserves a separate quality fix, not a claim that the movie leaked unrelated pixels. Check prompt exclusions and screenshot-only fallback without claiming a new Display/Region privacy guarantee. The Swift fixture calls the production writer and validator ABI, but a passing fixture alone cannot prove every application-level fallback. Do not record Kit's desk Mac.
